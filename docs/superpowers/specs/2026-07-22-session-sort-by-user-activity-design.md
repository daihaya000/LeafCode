# セッション一覧を最新ユーザー操作順に並べる設計

## 背景

現在のセッション一覧は `session_bindings.updated_at` を降順に比較しているが、既存セッションへの新しいユーザー指示送信時にこの値が更新されない場合がある。そのため、ユーザーが直近で操作したセッションが一覧の先頭へ移動しない。

## 目的と範囲

- 通常プロンプト、再実行、コマンドなど、ユーザーがセッションへ送信する操作の開始時刻を一覧順に反映する。
- 指示送信直後にサイドバーへ反映する。
- 並び替えは現在の構成を維持し、各プロジェクト内のセッション順だけを変更する。
- ページ再読み込み後や別タブでの再取得でも同じ順序を維持する。

## 非目的

- プロジェクト自体の並び順を変更しない。
- OpenCodeの全メッセージ履歴を一覧表示のたびに取得して推測しない。
- タイトル変更、セッション復元、単なる一覧閲覧をユーザー指示として扱わない。

## 採用方針

送信開始時に `session_bindings.updated_at` を更新する。既存のタスクサービスとSidebarが行っている `updatedAt` 降順ソートを再利用する。

この方式は、送信時刻をサーバーに永続化でき、OpenCodeのメッセージ履歴を全セッション分取得する必要がない。フロントエンドだけの一時的な並び替えよりも、再読み込み・別タブ・別端末で一貫した結果になる。

## データフロー

1. `sendPrompt` または `sendCommand` が呼ばれる。
2. 現在表示中のタスクIDとセッションIDを使い、対象バインディングを検証して更新時刻を更新する処理を呼ぶ。
3. 既存のOpenCode送信処理を開始する。
4. 送信処理の成功・失敗にかかわらず、クライアントはタスク一覧変更イベントを発火する。
5. Sidebarが `/api/tasks` を再取得し、更新された `updatedAt` により対象セッションを同一プロジェクト内の先頭へ移動する。

更新時刻の処理はベストエフォートとする。更新失敗で本来の送信処理を失敗扱いにせず、送信エラーの原因を隠さない。送信開始時に更新した時刻は、送信失敗後も戻さない。

## APIと整合性

- セッションIDだけで任意のバインディングを更新せず、タスク（workspace）とセッションの組み合わせをサーバー側で検証する。
- 通常プロンプトとコマンドは同じ更新処理を共有する。
- 新規セッション作成時の既存のバインド時刻、タイトル更新、マニフェスト復元の挙動は変更しない。
- 既存の一覧ソートの比較対象は `TaskSummary.updatedAt` のままとし、同フィールドを最新ユーザー操作時刻として扱う。

## エラー処理

- セッションが未準備、対象タスクが存在しない、またはバインディングが一致しない場合、時刻更新はスキップまたは警告可能な非致命エラーとする。
- OpenCodeへの送信エラーは従来どおり呼び出し元へ返す。
- サイドバー再取得の失敗は既存の一覧更新失敗として扱い、次回の可視化・ポーリング・イベントで再試行できる状態を維持する。

## 検証方針

自動テストで次を確認する。

1. 通常プロンプト送信開始時に対象バインディングの時刻更新が呼ばれる。
2. コマンド送信開始時に同じ時刻更新処理が呼ばれる。
3. 複数セッションの `updatedAt` が最新操作順に並ぶ。
4. 時刻更新処理が失敗してもOpenCode送信処理は不要に失敗しない。
5. 送信直後にサイドバーのタスク一覧再取得イベントが発火する。
6. TypeScriptの型チェックと関連テストが通過する。

## 受け入れ条件

- ユーザーが既存セッションへ通常プロンプト、再実行、またはコマンドを送ると、送信直後にそのセッションが所属プロジェクト内の先頭へ移動する。
- ページを再読み込みしても同じ順序になる。
- 送信失敗時に、送信エラーの表示や既存のセッション状態処理が壊れない。
- 無関係なセッションやプロジェクトの順序は変更しない。
